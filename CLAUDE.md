# Контекст проекта для Claude

Сервис уведомлений в Telegram о матчах команд CS2 на HLTV. Python, один
процесс, запуск в Docker. Несколько аккаунтов Telegram, у каждого свой список
команд и свои глушения; список правится через бота, `.env` даёт только белый
список и первый посев. Пользователь один, веб-интерфейса нет — интерфейс это чат с
ботом.

Общее описание — [README.md](README.md). Как устроено и почему —
[docs/architecture.md](docs/architecture.md). **Прочитай его перед любой
доработкой**: почти каждое решение там родилось из наблюдения за живым HLTV, и
без этого контекста часть кода выглядит переусложнённой и её тянет «упростить».

## Правила работы

**Документацию держать в актуальном состоянии.** Меняешь поведение — правь
документ в том же коммите, а не «потом»:

| Что изменилось | Что править |
|---|---|
| появилось/изменилось событие, команда бота | `README.md`, `docs/operations.md` |
| решение, компонент, механика источника | `docs/architecture.md` |
| осознанно что-то не обрабатывается | `docs/known-limitations.md` |
| переменная окружения, частоты | `.env.example`, `docs/operations.md` |
| деплой, CI, теги образа | `docs/deployment.md` |
| новое наблюдение за поведением HLTV | соответствующий `docs/recon/R*.md` |
| ловушка, на которой сам обжёгся | этот файл, раздел «Грабли» |

**Не выдумывать структуры источника.** Если не видел реального ответа сервера —
не знаешь, как он устроен. В сети полно статей 2015–2018 годов про HLTV с
адресами вида `scorebot.hltv.org:10022` — это неактуально. Источник истины —
`docs/recon/` и фикстуры.

**Уважать источник.** Потолок 1 запрос в 30 секунд зашит в код и конфигом не
поднимается. Никаких параллельных пулов, ротации прокси, решателей капчи. `403`
означает «отойди», а не «повтори через секунду».

**События рождаются только на переходах состояния.** Это не стиль, а
единственное, что спасает от лавины дублей. Подробно — в архитектуре.

**Тесты — по фикстурам, не по живому источнику.** Матчи редки, а овертайм,
обрыв связи и мультикилл по заказу не воспроизводятся.

**Проверять на реальных данных, когда есть возможность.** Половина ошибок в
этом проекте нашлась не тестами, а прогоном против живого HLTV. Если идёт живой
матч — прогнать сервис в `DRY_RUN` и посмотреть логи.

## Грабли

Каждая стоила времени. Не наступать повторно.

**На нажатие кнопки надо ответить ВСЕГДА.** Без `answerCallbackQuery`
Telegram крутит индикатор до таймаута, и человек считает, что бот завис.
Отвечаем даже когда делать нечего.

**Список глушимых типов один** — `menu.MUTABLE`, из него же берётся
`MUTABLE_EVENTS` для текстовой `/mute`. Две копии разойдутся, и кнопка начнёт
глушить то, чего команда не умеет. E8 в список не входит намеренно: заглушив
тревогу, можно не узнать, что сервис ослеп.

**Обновление старой базы обязано сохранять журнал.** Ключи, записанные до
появления подписчиков, разово получают префикс чата
(`adopt_legacy_event_keys`). Без этого первый же запуск новой версии счёл бы
новым всё, что уже отправлял, и разослал историю заново. На это есть тест —
`tests/test_migration.py` собирает базу первой версии и открывает её текущим
кодом.

**Получателей считает ОДНО место — `notify/audience.py`.** Там же и проверка
паузы. Правило «проверить в двух местах» тут уже проваливалось дважды:
`subscribers_tracking` про паузу не знает, и сначала пауза не работала для
матчевых событий, потом — для живого сообщения со счётом. Появится третий путь
доставки — он обязан ходить туда же, а не заводить свой расчёт.

**Ключ журнала событий включает адресата** (`<chat>|<ключ>`). Без этого
событие об общем матче ушло бы только первому подписчику: уникальный индекс
отсёк бы остальных как дубль.

**Событие строится целиком от лица одной команды.** Взять контекст
канонической команды и подменить в нём только имя — так E9 про игрока второй
отслеживаемой команды получал соперником её же саму («FORZE — FORZE») и
перевёрнутый счёт. Развернуть это потом нельзя: `format.orient` видит, что
`team_id` payload'а совпадает с командой получателя, и считает, что
разворачивать нечего.

**Счёт разворачивается при отрисовке, а не в машине.** Событие ориентировано на
каноническую команду; `format.orient` переворачивает его тому, кто следит за
соперником. В машину эту логику тащить нельзя — событие одно, а получателей
много.

**Перспектива матча выбирается один раз и не меняется.** Её хранит
`matches.team_id` — команда, увидевшая матч первой, — и `canonical_team()`
читает именно её. Если позволить перезаписывать, добавление второй команды
перевернёт счёт, ключи станут зеркальными и всё уже отправленное разошлётся
заново. В `upsert_match` порядок аргументов COALESCE именно такой, и менять его
нельзя.

**Защита бесполезна, если стоит на том, что никто не читает.** Тот самый
COALESCE полгода охранял `matches.team_id`, пока все машины спрашивали
`canonical_team()`, а он возвращал `MIN(match_teams.team_id)` — и перспектива
исправно переворачивалась. Тест на это был, но проверял он неиспользуемый
столбец. Проверяй ту величину, по которой РАБОТАЕТ код.

**Флаг первого запуска — свой на каждую команду.** Общий сделал бы добавление
команды через бота шумным: E1 по каждому её сыгранному матчу.

**Одно поле состояния — один писатель.** Самый дорогой класс ошибок в этом
проекте. Машина страницы и живая машина делили `current_map_name` и делали по
нему выводы о собственной истории — и обе ошибались. Теперь у каждой своя
приватная памятка: `live_map_name` пишет и читает только живая машина,
`page_seen_utc` — только машина страницы. `current_map_name` остался полем ДЛЯ
ОТОБРАЖЕНИЯ, решения по нему принимать нельзя.

**Не выводить «я это уже видел» из last_source.** Живой фид переписывает
`last_source` несколько раз в секунду, поэтому у страницы признак «я этот матч
впервые вижу» был вечно истинным, и E6 со страницы молчал всё время работы
фида. Признак должен быть отдельным и монотонным.

**Страница кладёт в состояние ПРЕДСТОЯЩУЮ карту.** `_current_map` при
отсутствии идущей карты берёт первую несыгранную. Если сравнить это с картой
из фида, «начало карты» выглядит как «карта не менялась», и E5 не рождается.

**Тесты машин по отдельности не ловят дефекты стыка.** Оба бага выше прошли
мимо 175 тестов, потому что каждая машина проверялась изолированно. Есть
`tests/test_page_and_feed_together.py` — при доработке любой из машин
дополнять его.

**`[data-unix]` без скоупа берёт чужое время.** На странице матча первым в DOM
идёт виджет избранных матчей `.fbw-vp-header-time`. Нужен
`.timeAndEvent [data-unix]`, иначе сервис шлёт ложные E2.

**У идущей карты счёт тоже числовой.** «Есть счёт — значит сыграна» неверно:
это текущий счёт. Классы `won`/`lost` не спасают, ими помечен текущий лидер.
Признак — ссылка `.results-stats`.

**`readyForMatch` принимает JSON-СТРОКУ, не объект.** С объектом сервер молчит:
соединение живо, ошибки нет, кадров нет.

**Подписываться можно только после пакета `40`.** На реконнекте он приходит не
вместе с handshake. Отправишь раньше — тот же молчаливый отказ.

**Лог фида проигрывается заново при каждом подключении.** На серии из двух карт
насчитывалось 150 событий `MatchStarted`. Поэтому решения принимаются по кадрам
`scoreboard`, а лог не используется нигде.

**Websocket у scorebot закрыт (403), работает polling.** Проверено с любыми
заголовками, куками и профилями impersonation, включая `curl_cffi.ws_connect`.

**Таймаут long-poll — не обрыв.** Фид молчит в паузах, весь перерыв между
картами проходит так. См. `FeedIdle`.

**Фраги в кадре накоплены за КАРТУ, не за раунд.** Без сброса базы отсчёта на
каждом раунде каждый следующий раунд выглядит мультикиллом.

**Счёт привязывать к `ctTeamId`/`tTeamId`, а не к стороне.** После перерыва
стороны меняются местами.

**«Первое наблюдение» — это первое СО СТРАНИЦЫ МАТЧА.** Строку состояния
заводит опрос расписания, поэтому проверка «состояния ещё нет» почти всегда
ложна, и карты, доигранные до начала наблюдения, получали E6 задним числом.

**Обычные HTTP-клиенты получают 403.** Отсев по TLS-фингерпринту, а не по
заголовкам. Их перебор бесполезен — только `curl_cffi` с impersonation.

**Разные аккаунты — ОДНА переменная `TELEGRAM_CHAT_ID`, id через запятую.**
Первый в списке основной: посев команды из `TEAM_ID` и одиночный режим
адресуются ему (`config.main_chat_id`, не `config.chat_id` — второе теперь
сырая строка списка). `TELEGRAM_ALLOWED_CHATS` убрана; о её присутствии в
окружении сервис предупреждает при старте, потому что молча пустой белый
список выглядит как «бот умер».

**Очередь на остановке не отменяют.** Отмена посреди `send_message` оставит
сообщение отправленным, но не отмеченным в базе, и при следующем запуске оно
уйдёт человеку второй раз. Задача очереди выходит сама по флагу остановки и
делает последний проход с дедлайном; `__main__` ждёт её через `wait_for`, а
гасит отменой только всех остальных.

**`HTTP_PROXY` в верхнем регистре libcurl игнорирует.** Намеренно, наследие
CGI. А в `compose.yaml` пишут именно так, поэтому переменные читает сам сервис
(`proxy.py`) и передаёт в сессию явно. Там же неочевидное: при попадании в
`NO_PROXY` прокси выставляется в ПУСТУЮ СТРОКУ, а не «не выставляется» — иначе
libcurl подхватит переменную окружения сам и обход не сработает.

**Логи на русском под Windows роняют обработчик.** Консоль в cp1252.
`setup_logging` принудительно переводит потоки в UTF-8; в скриптах —
`PYTHONIOENCODING=utf-8`.

**Экранирование в патч-скриптах.** `\n` внутри питоновской строки, которой
патчишь файл, превращается в настоящий перенос и ломает исходник. Для правок
кода надёжнее Edit, а не `str.replace` из heredoc.

## Команды

```bash
python -m pytest                                    # 311 тестов
PYTHONIOENCODING=utf-8 PYTHONPATH=src DRY_RUN=true python -m hltv_notify
PYTHONPATH=src python -m hltv_notify.replay <дамп.gz> --team-id N --match-id M --twice
python scripts/fetch_fixtures.py                    # пересобрать HTML-фикстуры
python scripts/record_scorebot.py <match_id> <файл.gz> --duration 3600
docker compose up -d --build && docker compose logs -f
```

Git: репозиторий **свой**, внутри папки проекта (родительская `D:\Documents` —
чужой репозиторий, туда коммитить нельзя). Remote по **SSH**
(`git@github.com:v1p3rrr/hltv-notificator.git`) — HTTPS-креды в credential
manager не подходят.

## Как снимать новые фикстуры

Живой матч найти на `hltv.org/matches` (секция live). Дальше:

* HTML страниц — `scripts/fetch_fixtures.py`, правкой списка `PAGES`;
* дамп фида — `scripts/record_scorebot.py <match_id> <файл> --referer <url матча>`.

Ценны те моменты, которые не воспроизводятся: **граница карт**, овертайм,
обрыв связи, мультикилл. Если ловишь живой матч — бери тот, что **на первой
карте**, тогда граница точно случится.

Дамп схлопывает подряд идущие одинаковые кадры и помечает обрывы — на этом
строятся тесты дедупликации.

## Состояние

Этапы 1–5 плана закрыты, плюс сверх плана: несколько отслеживаемых команд с
управлением через бота, живое сообщение со счётом, алерты о мультикиллах и
сторож деградации с порогом по срочности.

Не сделано и обсуждалось: мобильный JSON-эндпоинт HLTV как второй источник
расписания (требует проксирования трафика приложения, см. recon/R3).

## Чего не делать

Не расширять область на другие игры и сайты. Не делать веб-интерфейс,
дашборды, метрики Prometheus, микросервисы. Не поднимать частоту опроса, чтобы
«успевать» — если не успеваем, это аргумент за живой фид. Не хранить секреты в
репозитории. Не отправлять уведомления в обход машины состояний.
